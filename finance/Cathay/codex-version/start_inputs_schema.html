Payload Contract

Dify START Inputs Schema

START node 需要完整接收前端 payload，讓 workflow 不靠自然語言猜 user_type、route_stage、risk_level 或 mock data 使用限制。

本頁重點

欄位總表 自動帶入 Payload 範例
提示 布林值建議用字串 "true" / "false" 傳入，降低 Dify URL query、DSL 匯入與前端 JSON 型別不一致的風險。

欄位總表

欄位用途範例值必填對內 / 對外差異
user_type分流 internal / external。internal_employee, external_customer是前端固定帶入，不開放手動改。
user_role員工或客戶角色。customer_service, customer對內是對外不顯示內部角色。
department員工部門。call_center, compliance對內是對外留空。
channel來源通路。internal_workspace, customer_chatbot是由入口自動帶入。
business_line金融業別。banking, credit_card是對內由產業卡片選；對外由服務卡片或分類推論。
service_id服務或情境代碼。credit_card_dispute是用於追蹤該次 demo route。
route_stage回答路線。status_lookup, handoff_risk是對內與對外枚舉不同。
scenario_type細分情境。fraud_warning建議協助 intent classifier。
risk_level初始風險。normal, high, critical是Risk Gate 可上修，不可不安全地下修。
permission_level權限層級。public, case_owner是對外固定 public。
auth_status驗證狀態。verification_required, verified是正式資料需驗證，但 demo 不查正式系統。
service_relationship服務關係。case_owner, none是對內用於 Permission Gate。
approval_required是否需審批。true是對外不揭露審批細節。
audit_required是否產生 audit log。true是對內顯示 mock audit；對外不顯示。
handoff_required是否需轉真人。true是高風險或要求真人必須為 true。
faq_sourceFAQ/KB 來源。/faqs/credit_card.md建議用於引用依據。
answer_contract回答格式契約。internal_governed_reply是決定固定段落。
expected_sections預期輸出段落。問題理解|下一步是對內 11 段；對外 6 段。
mock_data_available是否有 mock data。true是有 mock profile 時自動 true。
mock_data_sourcemock data 來源。frontend_demo是不可填正式核心系統。
mock_data_summarymock 摘要。known_status=疑似盜刷建議給模型優先讀取。
mock_data_contractmock 使用限制。不可宣稱正式查詢是對內/對外原則一致。
mock_customer_profilemock 客戶 profile JSON。{"customer_id":"CUST-001"}否只能是假資料或遮罩資料。
data_policy一般資料政策。mock_only_no_core_system_lookup是對外強調不揭露內部流程。
sensitive_data_policy敏感資料政策。never_request_password_otp_cvv_full_card是對內/對外都必須遵守。

自動帶入與可操作欄位

前端自動帶入

user_type、channel、audit_required、answer_contract、expected_sections、mock_data_contract、data_policy、sensitive_data_policy。

使用者可選

Internal 可選 business_line、route_stage、scenario_type。External 只選服務卡片或輸入問題，不直接調整風險或審批欄位。

# Claude Review 與改版計畫

判讀日期：2026-07-03。內部診斷紀錄；對外提案見 `index.html`。診斷依據為實際閱讀原專案原始碼：`external/`、`internal/`、`mock-data-overview.html`、`faqs/`、`dify-dsl/`。

## 診斷

**已具備的資產（保留，不重做）：**

- 風險三級徽章：6 個情境帶「一般 / 注意 / 高風險」，連動警示與禁止提問清單。
- 邊界契約：各業別定義「同仁可說 / 先確認 / 不可說」與「客戶回覆 / 轉真人條件」。
- 三路線升級：自助排除 → 複雜狀況 → 高風險轉接，對應 Dify route_stage。
- 透明 payload：business_line、service_id、risk_level 等輸入攤開可複製。
- 雙契約分離：對內工作台語言與客戶端語言分開，內部規則不外洩。

**三個缺口（治理停在靜態腳本，未成為 runtime 機制）：**

1. 風險分級靠使用者選卡片，不是系統判斷意圖與信心。真實客戶不會先自我分類再提問。
2. 回答層無 citation；客服修正無回流路徑，品質不收斂。
3. 轉真人與護欄命中只是畫面動作，無事件紀錄，無法審計與回放。

與 Codex-version 的差異：Codex 版診斷為「呈現太滿、缺治理」；本版認為治理雛形已存在於 demo，缺的是 runtime 化與可量測，故主張升級而非重做。

## 方案

| 缺口 | 機制 | 最小可交付 |
|------|------|-----------|
| 邊界寫死 | 風險 / 信心閘門 | 意圖信心 + 檢索命中分數決定回答或轉真人，門檻可調可回放 |
| 回答無來源 | Citation-first 回答卡 | RAG 透傳 metadata，顯示來源頁面與知識版本；修正入知識庫候選 |
| 紀錄只在畫面 | 審計事件流 | 每筆對話落事件：意圖、來源、風險、信心、護欄命中、處置 |

**MVP：**一個低風險切面（信用卡 FAQ 或開戶），三機制串成端到端；審核視圖沿用 internal 工作台版型。

**邊界：**不改核心交易系統；GenAI 不碰個資、帳務、不可逆交易；不做全通路整合；不做監控大屏。

## 90 天：先量測、再閘門、後回流

- **0–30 量測**：不改回答行為，每筆對話落審計事件。產出基準數據（可追來源比例、高風險邊界占比）。
- **31–60 閘門**：依基準數據設信心 / 風險門檻，低信心與高風險轉真人；上線 citation 回答卡。產出閘門命中率、誤攔率、轉真人量變化。
- **61–90 回流**：客服修正入知識庫候選，每週 knowledge gap list。產出 Pilot 報告與擴大建議。

順序理由：門檻無基準數據就是拍腦袋 —— 過嚴塞爆真人，過鬆形同虛設。

## 指標與驗收

硬性驗收：每筆 pilot 對話四件事可查 —— 來源、信心、風險、處置（事件覆蓋率 100%）。

- 紅線測試回放：高風險題庫 100% 不直接生成最終答案。
- 低風險回答附來源比例：目標區間依基準數據訂（假設 85–95%）。
- 閘門品質：低信心轉真人的事後判定正確率（比轉真人率重要）。
- 回流速度：修正入知識庫候選中位天數（假設 7 天內）。
- 可讀性：客服 30 秒內看懂 AI 判斷依據（可用性測試）。

標示「假設」者以 0–30 天量測修正。
